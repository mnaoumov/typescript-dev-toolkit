# AGENTS.md

## Project overview

`@mnaoumov/typescript-dev-toolkit` — Generic TypeScript project tooling: build, lint, format, spellcheck, test, gate and release scripts.

It depends on `@mnaoumov/typescript-lib` only, and every other `@mnaoumov` repository builds, lints, tests and releases with it. It is tooling: it runs in Node, so all of `src/` is linted as scripts.

- **It builds itself from its own sources.** `scripts/*.ts` import `../src/*.ts`, never `@mnaoumov/typescript-dev-toolkit/...`: a package cannot install itself, and building from the sources is what lets a change here be used by its own gate before it is released.
- The shared ESLint config is two layers: the generic one here (`src/linters/eslint-config.ts`, `defineEslintConfigs`), and the Obsidian one in `@mnaoumov/obsidian-dev-toolkit`, built on `getTypeScriptEslintConfigs`. Nothing here may name `obsidianmd`, `manifest.json` or `desktop-*`; a test asserts it. The generic in-house rules are registered under the `typescript-dev-toolkit` namespace (`IN_HOUSE_ESLINT_PLUGIN_NAME`), and `obsidian-dev-toolkit` registers its own rules under its own name, as a separate plugin. Until `2.0.0` every in-house rule sat under one `obsidian-dev-utils` namespace. Old ids were not kept as deprecated aliases, because an alias keeps no consumer green: measured on ESLint 10.11.0, a disable comment naming a registered rule that is off is reported as an unused directive, and the renamed rule still reports. A consumer replaces `obsidian-dev-utils/<rule>` with the new id when it takes the major.
- **`unicorn/prefer-logical-operator-over-ternary` is off, replaced by `typescript-dev-toolkit/prefer-logical-operator-over-ternary`**, which runs unicorn's rule and adds the fix unicorn withholds in a TypeScript file when one branch is a boolean literal (`a ? false : b` → `!a && b`). Without it `unicorn/prefer-ternary` fixed `if (a) { return false; } return b;` into that ternary and `lint:fix` stopped on an error it had just made. Its test runs both fixes and asserts nothing is left. Since unicorn 79 the shape is reported for a test of any type (only the other branch must be boolean), so an un-negated test the type checker cannot prove boolean is fixed as `!!a && b`, never `a && b`, which would return a falsy `a` (`null`, `0`) where the ternary returned `false`. `!!` rather than unicorn's `Boolean(a)`, because TypeScript narrows on it.
- **unicorn 79's new recommended rules are adopted except two, turned off in `getUnicornConfigs` with the reason beside each**: `no-asterisk-prefix-in-documentation-comments` (it rejects the ` * ` block-comment style every file here uses; 1,553 reports) and the new `repo` → `repository` entry of `name-replacements` (`repo` is git's own word, and following it renamed exported API such as `RepoPaths` and `DocsSiteConfig.repo`). Before adopting a later unicorn major, diff its `configs.recommended` against the installed one and lint this repository with it, as was done for 79.
- **`typescript-dev-toolkit/readonly-interface-members` requires readonly property signatures in every interface and object type alias, including nested object types.** It replaces `readonly-params-options-result-members` without an alias. Mutable state needs an explained disable on the property; methods, index signatures and local object annotations are outside this rule. A readonly property holding an array still permits array mutation. The fixer inserts before the whole property so computed keys retain their brackets.
- **`typescript-dev-toolkit/readonly-member-arrays` is a separate opt-in collection policy.** Enable it explicitly to require readonly array types on interface and object-alias properties, including unions and nested object properties. It offers reviewed suggestions for `T[]` and the builtin `Array<T>` when no local binding shadows it, never an autofix: changing a public array type can break mutation and assignability in consumers. It checks only the member array, leaving inner arrays, tuples, aliases to arrays, method signatures and arrays inside other generic containers outside its scope. The shared configuration leaves it off; mutable collections and readonly property references are independent choices.
- **`typescript-dev-toolkit/no-keyword-identifiers` requires `$name` for bare keyword and colliding global binding names** (`object`, `string`, `number`, `boolean`, `symbol`, `bigint`, `undefined`, `arguments`, `function`, `module`, `event`). It checks declarations through ESLint's scope manager; compounds, property keys and builtin reads remain legal. Renames are suggestions, never autofixes. Suggestions update references and preserve type annotations, but are withheld for class names, exports, imports, property patterns, parameter properties and existing `$name` bindings; those need a manual rename that preserves the contract.
- **dprint owns layout. The shared ESLint config keeps only the nine `@stylistic` rules dprint cannot express** (`getStylisticConfigs`, each with a comment saying why), not `stylistic.configs.recommended`. Before `3.0.0` the whole preset ran next to dprint and the two fought: `wrap-iife` added parentheses that dprint stripped, `jsx-quotes` undid `quoteStyle`, and `operator-linebreak` needed a disable comment where dprint broke the line differently. Each clash was found only when a gate failed. `src/eslint-formatters.integration.test.ts` formats violating fixtures with `dprint.json`, and again with the shared Prettier and Biome configurations, fixes them with every enabled `@stylistic` rule, and formats them again. It fails when the second format changes anything or a report is left. The same nine rules pass against all three formatters, so the ESLint config needs no per-formatter variant; add one only when a formatter measurably fights a rule there. Before adding a `@stylistic` rule, check that no formatter already fixes that shape (format a violating probe and lint it), and add the shape to that test's fixture. `dprint.json` sets `jsx.quoteStyle: preferDouble`, because `jsx-curly-brace-presence`'s fix writes double quotes. It also sets `useBraces: always` to agree with ESLint's `curly`, and `importDeclaration.sortNamedImports: maintain` so ESLint alone sorts named imports by their local aliases; dprint otherwise sorts by imported names. The integration test separately runs lint fixes, dprint, lint and another fix/format cycle over single-line control-flow bodies and aliased value/type imports. Consumers with their own `dprint.json` need these settings there; the formatter uses the project's configuration as given.
- **`format()` and `lint()` have one module per tool (`formatters/dprint`, `formatters/prettier`, `formatters/biome`, `linters/eslint`, `linters/biome`) and a dispatcher each (`formatters/auto`, `linters/auto`) that picks the tool from the project's config files**: formatter `dprint.json`, then a Prettier config, then `biome.json(c)`, else dprint; linter `eslint.config.*`, then `biome.json(c)`, else ESLint. This repo's own scripts call the dispatchers. Prettier and `@biomejs/biome` are optional peers. Their shared configurations ship as `assets/prettier.json` and `assets/biome.json` (found by `getSharedConfigFilePath`, walking up from the module), matched to the dprint style where each tool allows, with a 120-column line because both re-wrap to it. **Biome cannot be handed the shared config with `--config-path`**: it resolves the VCS root against the config file's folder, so from `node_modules` it looks for `.gitignore` there and fails, and an absolute `--vcs-root` crashed Biome 2.5.15 outright. So `ensureBiomeConfig` writes a project `biome.json` that `extends` it. Biome also finds `.gitignore` only inside a git repository. Prettier takes the shared config by `--config` when the project has none, and excludes `**/*.md` and lockfiles with negated patterns, which apply to explicit paths too.
- **`test()` / `testCoverage()` / `testWatch()` work the same way: one module per runner (`test-runners/vitest`, `test-runners/jest`) and a dispatcher (`test-runners/auto`) that picks `vitest.config.*`, then `jest.config.*` or a `jest` key in `package.json`, else vitest.** `vite.config.*` deliberately does not count. This repo's own `test*` scripts call the dispatcher, except `test:integration`, which names vitest projects. Jest and ts-jest are optional peers. `defineJestConfig` (`test-runners/jest-config`) and the jest runner decide ESM by the same rule, `package.json` `"type": "module"` (`isEsmPackage`), and the runner adds `--experimental-vm-modules` to `NODE_OPTIONS` for it. ts-jest runs with `isolatedModules`, so jest, like vitest, does not type-check. `src/jest-runner.integration.test.ts` runs real jest on a temp ESM fixture whose `node_modules` is a junction to this repo's, and its failing-threshold case is what proves the JSON `--coverageThreshold` argument survives the Windows shell.
- `lint()` (`src/linters/eslint.ts`) reads ESLint's exit itself rather than letting `execFromRoot` throw: `classifyEslintExit` keeps findings (exit `1`, no `Oops! Something went wrong!` banner) apart from a run that never finished linting (a rule crash, a broken config or path, a signal, an NT status exit such as `0xC0000005`), and `describeFailureToLint` names which. The stderr fixtures in `src/eslint.test.ts` are real ESLint output; keep them so.
- **All three Vitest wrappers honor a positive safe-integer `BULK_CORES` budget.** Only in bulk mode, they load the optional `vitest/node` resolver to find the selected projects' limits, including percentages and `fileParallelism: false`, before launching the CLI. The child gets the minimum of the budget, ordinary Vitest worker default, inherited `VITEST_MAX_WORKERS` and configured worker limits. That minimum applies to the entire invocation: Vitest's CLI and environment limits overwrite project limits, so blindly setting either can increase a serial project's workers. Worker environment resolutions are serialized. The inherited worker variable is temporarily removed during resolution and restored before spawning, including when resolution fails. Unbudgeted invocations keep their existing defaults. `src/vitest-workers.integration.test.ts` checks real runs and coverage with serial projects beside a percentage-configured project.
- **`scripts/test.ts`, `test-coverage.ts` and `test-watch.ts` forward their CLI arguments as `additionalArguments`**, which every runner appends after its own. `assertNoOwnedArguments` (`src/test-runners/forwarded-arguments.ts`) refuses one naming an option the wrapper sets (projects, coverage, run/watch mode), because vitest's `--project` is additive and a forwarded `--coverage.thresholds.*` would lower the gate. Until then `npm test -- <file> --maxWorkers=2` silently ran the whole suite. `src/test-scripts.integration.test.ts` runs the real `scripts/test.ts` with a file filter.
- `defineEslintConfigs({ minimumNodeVersion })` pins `eslint-plugin-n`'s Node version; without it the plugin reads `engines`.
- `generateLibraryExports({ sourceCondition })` writes a source export condition only when asked: a repository holding several packages that import each other needs one, nothing else does. `generateLibraryExports({ additionalExports })` adds entries for files no source folder builds (`obsidian-dev-toolkit`'s `./tsconfig/*` and `./types/*`) after the generated ones, inside the change check; a key a source folder already generates throws rather than overriding it.
- `src/library-build.ts` is the library pipeline every package's `build:*` scripts call (`buildCleanLibrary`, `generateLibraryIndex`, `buildLibraryTypes`, `buildLibrary`, `generateLibraryExports`, `runBuildSteps`). `generateLibraryIndex({ excludeFromIndex })` leaves the named modules or folders (paths from the package root) off the generated barrels while they are still built and reachable through their own subpath: a module bound to an optional peer, or one that calls a test runner at load time, would otherwise make every barrel import throw without that peer. A path that names nothing the barrels would export throws, so a rename cannot put the module back silently. `buildLibraryTypes` scans every source file, tests included, for a `/// <reference lib=…>` directive and copies each into the published declarations, so a source that merely CONTAINS that text adds a `lib`; spell such a string apart. Every declaration but the root one references the directives-only `library-references.d.{mts,cts}` it writes, never the root barrel: the barrel re-exports every module, so a consumer of one subpath type-checking with `skipLibCheck: false` needed every optional peer (`vitest`) installed. `src/library-build.integration.test.ts` checks that against the built `root` subpath. `library-references` carries only the language libs (`es*`, `esnext.*`); the host libs (`dom*`, `webworker*`, `scripthost`) and `types="node"` go only into the declarations that name one of their globals, which `collectEnvironmentDirectives` finds by resolving every name with the type checker. A global both the DOM and `@types/node` declare (`setTimeout`, `AbortSignal`) is taken from the DOM. A lib replaced by a package (`@typescript/lib-dom`) is named by its path, because its file is `index.d.ts`.
- **`validateDependencies` (`src/validate-dependencies.ts`, the `build:validate-dependencies` step, last in `LIBRARY_BUILD_STEPS`) fails the build when the published output imports a package a consumer does not install.** Every bare specifier in `dist/lib` and `bin` (code and declarations, collected with `typescript`'s `preProcessFile`, so strings and comments do not count) must name a package in `dependencies`, `optionalDependencies` or `peerDependencies`, the package itself, or a builtin. A builtin is anything Node's `isBuiltin` knows, any `node:`-scheme specifier (no package name can start with `node:`), and Electron's `electron` (with its subpaths) and `original-fs`: Node's list lacks Electron's modules, so `window.require('node:original-fs')` in code shipped for an Electron renderer was reported as an undeclared package. A declaration file's import may also be served by the package's `@types` one (`estree` → `@types/estree`), and only a declaration file's: a runtime import of `estree` still needs `estree`. A package in `devDependencies` only passes every other check here and fails in the consumer with `Cannot find module`. Its first run here found `ts-estree-node.d.{cts,mts}` importing `estree` with `@types/estree` installed only transitively, which is why that is a dependency.
- **An unbundled build (`bundle: false`) gets no preprocess banner.** `preprocessPlugin` then parses each emitted module and prepends a preamble with only the shims that module needs: `ensureBrowserProcess` for a free `process` read or a bare non-`node:` import, `ensureDisposeSymbols` for `Symbol.dispose` / `Symbol.asyncDispose` / esbuild's `__knownSymbol`, and the `__name` shim for a free `__name`. The caller's `additionalBannerInitFunctions` go into every module. It shifts the inline source map by the lines it adds. A bundled build, or one that leaves `bundle` unset, keeps the build-wide banner. `fixEsmPlugin` writes its default-extraction helper inline rather than calling a `__extractDefault` global, because a module with no preamble has no such global.
- **`svelteWrapperPlugin` preprocesses with `createSveltePreprocessor` (`src/bundlers/esbuild-impl/svelte-preprocessor.ts`), not `svelte-preprocess`.** `<script lang="ts">` is transpiled by esbuild under `verbatimModuleSyntax`, as Svelte's `vitePreprocess` does, so a markup-only import survives and a type import needs `import type`. Any other script or style language goes to `svelte-preprocess`, now an optional peer loaded only then, and fails naming it when it is absent. It was a dependency until 2026-10-28, and its optional `@babel/core` `^7` peer made every install that also had Stryker (which brings Babel 8) print an `npm warn` about overriding that peer dependency; never install it here, which is why the fallback imports it through a variable specifier. `svelte-wrapper-plugin.integration.test.ts` compiles a real component through esbuild-svelte, and runs the missing-package case in a child Node process, because under Vitest that import fails with Vite's own message.
- **`svelteWrapperPlugin` (`src/bundlers/esbuild-impl/svelte-wrapper-plugin.ts`) loads `esbuild-svelte` with `import()` inside `setup`, never at module load.** `esbuild-svelte` imports `svelte/compiler` when it loads, and `obsidian-dev-toolkit`'s esbuild build adds the plugin to every build, so a static import made `svelte` a requirement of every build. npm installs that peer by itself; Yarn 1 does not, and a Svelte-free project failed `yarn build` on `Cannot find module 'svelte/compiler'`. When the load fails on a missing `svelte` (`isMissingSveltePackageError`), `setup` registers a `.svelte` loader that fails naming the package, so only a build that reaches a component fails.
- `readIndexContent` (`src/git.ts`) reads a file's STAGED blob as raw bytes by spawning `git cat-file` itself, never through `execFromRoot`, which decodes stdout as UTF-8 and strips a trailing newline. It is for a gate run from nano-staged, whose parallel task groups make the working tree race `lint:fix`. `src/git.integration.test.ts` pins it against a real git.
- The markdownlint `lint()` (`src/linters/markdownlint.ts`) takes `linkCheckExcludeGlobs`, which keeps matching files out of the `linkinator` pass only: a docs site's pages link base-absolutely (`/<site-base>/...`) and resolve only against the built site, which checks them itself. There is no `docs/**` default, because a repository without a built site would silently lose its link check. When the exclusions leave no file, the `linkinator` call is skipped, because `linkinator` with no location prints its usage and fails. It uses `node:path`'s `matchesGlob`, hence `engines.node >= 22.5.0`. **A link answering `429` or `408` passes with a `[WARN]` (`--status-code 429:warn --status-code 408:warn`)**, because forum.obsidian.md rate-limits a CI runner's burst, shields.io answers `408` for a GitHub-backed badge while its upstream is slow, and neither says anything about whether the link exists; `--retry-errors` retries neither (only `0`, `5xx` and a `429`), and the shields host is deliberately not warned as a whole, since a badge with a wrong path still answers a real `404`; `--retry-errors-jitter` is in milliseconds, so it is `5000`, and the earlier `5` let every retry land in the same instant. Measured against `https://httpbin.org/status/429` and `/status/408` on `linkinator` 8.1.0: exit 0 with a warning, and exit 1 without the flag.
- **`LINK_CHECK_SKIP` (`src/link-check-skip.ts`) leaves links out of the markdown `linkinator` pass for one run**: comma-separated entries, a `://` entry is a URL prefix, anything else an exact host. It is read like every variable here, `.env` included, and the docs say to set it per command, because a lasting skip lets links go stale. Every skipped link and every entry that skipped nothing prints a `WARNING`; that scan is textual, so it also names a URL in a code span. **The patterns reach `linkinator` through a temporary `--config` file, never `--skip`**: on Windows the `npx` and `.bin` shims re-expand the arguments unquoted, and the `|` in a pattern was run as a pipe (`'$)' is not recognized as an internal or external command`). `--config` replaces the project's own `linkinator.config.json`, so `mergeLinkinatorSkipConfig` carries that file's settings and `skip` list over.
- **`getBulkConcurrency` (`src/bulk-concurrency.ts`) caps OG image rendering (normally 10), built-site external probes (20), and markdown linkinator (100) to a positive safe-integer `BULK_CORES` budget.** It reads the environment at invocation time, ignores missing or malformed budgets, and never raises the ordinary default. The markdown checker uses a 30-second request timeout and retains `--retry-errors` with count 3 and jitter 5000, but omits `--retry`: that separate mode honors an arbitrarily long `Retry-After` even for a 429 already accepted as a warning. Timeouts and exhausted error retries still fail the check.
- **`src/docs-site/` is the documentation-site builder every `@mnaoumov` package's site is built with** (moved from `obsidian-dev-utils`' `scripts/docs-gen`). A site describes itself once, as a `DocsSiteConfig` (`{ repo, title }` plus optional overrides) in a module both its `astro.config.ts` (`defineDocsSiteConfig`) and its `docs:*` scripts (`buildDocsSite` / `devDocsSite` / `previewDocsSite`) import; everything that was hard-coded to `/obsidian-dev-utils` is derived from `repo`. Astro, Starlight, Sätteri, satori, resvg, ts-morph, yaml and `typedoc-plugin-mdn-links` are OPTIONAL peers: only `src/docs-site/*` imports them, so a consumer that never builds a site never installs them. The generated root barrel re-exports `docs-site` as it re-exports the `vitest`-dependent `test-runners`, so a consumer imports a subpath.
  - **The files that are not TypeScript ship under `assets/docs-site/`** (the API page components, `SiteTitle.astro`, `global.css`, the Inter fonts), found by `getDocsSiteAssetsDirectory` walking up from the module, because it runs from `src/docs-site` here and from `dist/lib/<format>/docs-site` once installed. Generated pages import the components through the `@mnaoumov/typescript-dev-toolkit/docs-site-components` specifier, which `defineDocsSiteConfig` aliases onto that folder. `route-data` sits beside `astro-config` in every build, with the same extension.
  - **Cross-site links follow the declaration, not the name.** A type whose declaration resolves into `node_modules/<package>/dist/lib/{esm,cjs}/<path>.d.{mts,cts}` of a `packageSites` package (the five `@mnaoumov` sites by default; the documented package itself never) links to `<site>api/<path>/<Type>/`. Only class, interface, type alias and enum declarations are recorded: a function's name also matches ordinary words in type text, which is how a `resolve` import once linked a `resolve` property to `typescript-lib`'s `path/resolve`. A name two packages declare is never linked. Nor is a type declared in a module the owning site's generator skips (`@types`, `styles`, `test-helpers`, `index`, `__merged`, `setup`, `*-setup`): it has no page, and a package link would also shadow `externalTypeLinks`. The source walk and the linker share that rule through `src/docs-site/api-doc-documented-files.ts`. Ecosystem references (CodeMirror, Moment, Obsidian) are not generic: `obsidian-dev-toolkit` passes them as `externalTypeLinks`.
  - **Where a package's API surface differs, the site says so through `DocsSiteConfig`, never a fork of the generator.** `importStatement` builds each export's import statement (a package publishing barrel entry points; `undefined` shows none), `memberRouteSegment` overrides a member page's route segment, `excludedDirectories` adds to the `@types` / `styles` / `test-helpers` exclusions of the source walk (only: the cross-site linker cannot know another site's extras), and `genericTypeParameters` adds names never linked as types. `apiIndexIntro` replaces the root API page's generated intro (and, stripped, its `description`); without it, a site setting `importStatement` gets an intro that names no import subpath, since the hook, not the module path, decides where an export is imported from. `publicApiEntry` (e.g. `src/index.ts`) is for a package publishing ONE entry: the entry files are the modules that barrel re-exports (`readPublicApiBarrel`, parsed with `typescript` before the ts-morph project exists, so a cache hit stays cheap), the collected types are cut to its re-exported names by qualified id AFTER `resolveInheritedMembers` (so a public class keeps an internal base's members), the barrel itself is hashed, and import statements and the root index name the package root. A rename, a namespace re-export or a re-export from another package throws, since none can be documented under the name a consumer imports. Every one defaults to the generic behavior. A hook is hashed by its source into the generation cache, so changing it regenerates. A member's slug keeps its trailing underscores (`create__`), because stripping them gave `create__` and `create` one page and one silently overwrote the other.
  - **`repoHomepage` (`'off'` by default, `'check'`, `'set'`) is the only thing here that touches GitHub settings**, through `src/docs-site/repo-homepage.ts`: after the link check, `buildDocsSite` compares the repository's homepage with the site's `siteBaseUrl` and warns with the `gh repo edit --homepage` line, or sets it when the credentials can. It never fails a build, because a workflow's `GITHUB_TOKEN` cannot edit repository settings. It knows no account or origin of its own; a hub that lists the sites belongs to the hub, never here. This repo opts in with `'set'`, and `build-pages.yml` passes `GH_TOKEN` for the read.
  - **The external half of the link check retries a transient failure (a network failure, a `408`, a `429`, a `5xx`) with a doubling, jittered backoff that honors `Retry-After`, over a 45 s budget per URL, and caps the probes of one host at 8** (`collectBrokenExternalLinks`, `src/docs-site/link-check.ts`). A site linking its siblings probes thousands of URLs on `mnaoumov.dev`, and in CI GitHub Pages answers a burst of them with a `503` that is gone a moment later; three attempts a second apart failed a Pages build on 2026-10-16. A `5xx` that outlasts the budget still fails the build, as a `404` does at once: a warning nobody reads would let a dead link ship. An `https://www.npmjs.com/package/<name>` link is probed as `https://registry.npmjs.org/<name>`, because npmjs answers an unattended `fetch` with `403`; the markdown runner gives `linkinator` the same rewrite.
  - **A site links only to its dependencies, so the sites deploy in the release order** (typescript-lib, typescript-test-toolkit, typescript-dev-toolkit, obsidian-lib, obsidian-dev-toolkit), and the built-site link check passes because each site goes up after the ones it links to. Never add a `mnaoumov.dev` skip to get round the order.
- **The shared commitlint config (`commitlintConfig`, `src/commitlint-config.ts`) extends `@commitlint/config-conventional` by the ABSOLUTE path it resolves from its own module**, and the package is a dependency here. Commitlint resolves a bare `extends` name from the consumer's working directory, so the name worked only where the consumer declared the package itself or the package manager hoisted this one's copy. `obsidianDevUtilsConfig` is its deprecated old name, kept until the next major.
- **`src/upstream-sync.ts` is the upstream-sync core, moved from `create-obsidian-plugin`, and `src/upstream-sync-cli.ts` is its command**, shipped as the `sync-upstreams` bin and run on a schedule by the reusable `.github/workflows/sync-upstreams.yml` (`workflow_call`). Everything is driven by the consumer's `upstreams.json` and the handler commands it names, and all of git, `gh`, `fetch` and the shell go through the `SyncDependencies` interface, so the tests stand fixtures in for them. `bin/sync-upstreams.mjs` only imports the built `dist/lib/esm/upstream-sync-cli.mjs`: it sits outside `src/` so the shebang never depends on what the unbundled build prepends to a module (a preamble or the caller's banner), and keeping every line of logic in `src/` keeps it under the coverage gate. The workflow's usage example pins a release tag; move it when a release changes what the workflow needs. **A command's output reaches a PR body only through `cleanCommandOutput`**, which strips terminal control sequences in the byte form AND the caret-rendered `^[[32m` text (create-obsidian-plugin#2 carried only the caret form), and the handler and verify run with `NO_COLOR=1` / `FORCE_COLOR=0` but not `CI=1`, which changes what some tools do. A failed step's section opens with its lines that report the failure, ahead of the output tail. A sync whose branch already holds the result still rewrites the open PR's body, so a change to the body reaches existing PRs on the next run.
- **`testMutation` (`src/test-runners/stryker.ts`) is an on-demand Stryker run, never part of a hook or the gate, and `npm run test:mutation [<module.ts> ...]` runs it here.** With paths it mutates those modules and runs only their sibling `*.test.ts` files, which it hands to `vitest.stryker.config.ts` through `STRYKER_TEST_FILES` (`getStrykerTestInclude`), because `vitest.related` found no tests in the pilot. With none it runs everything with `--incremental`, and that takes about an hour. `defineStrykerConfig` (`src/test-runners/stryker-config.ts`) carries what that pilot measured. It runs `inPlace`, because the sandbox copy broke module resolution. It keeps `docs/` out, because copying 18k files there OOMed the main process. In place, Stryker puts the WHOLE tree back as it was when the run started, so `testMutation` refuses a dirty tree; do not edit during a run. `--logLevel debug` crashes the vitest runner (it `JSON.stringify`s a circular config). `/* v8 ignore */` lines show up as NoCoverage. The vitest runner must be 10.1.1 or later: 10.0.0 joined the describe chain with `' '` where vitest 5 matches `' > '`, so every mutant ran zero tests and Survived (stryker-js#6210). `stryker-config.ts` imports only `node:process` and uses only syntax Node can strip, because this repo's `stryker.config.mjs` loads it from `src/` through Node's type stripping. The package cannot install itself here. Measured on the first run here (2026-10-23): `jest.ts` 86.15%, `stryker.ts` 90.63%, `stryker-config.ts` 97.56%. Stryker and its runner are optional peers.
- `npm run test:integration` runs the integration project (real `markdownlint-cli2`, `cspell` and shell round trips). `scripts/helpers/echo-args.mjs` is its argument-echo fixture.

- **`typescript-dev-toolkit/prefer-noop-async` fixes preserve bindings.** The fixer reuses a visible value import of `noopAsync` from `@mnaoumov/typescript-lib/function`, including aliases, or adds a separate import with a collision-free name. Type-only imports and shadowed bindings are never reused. Hashbangs and directive prologues stay ahead of the new import. Scripts that cannot accept an ESM import retain the diagnostic without a fix. A `Promise` the code binds itself (a local, a parameter, an import) is not reported, because its `resolve()` need not be a no-op; the check resolves the reference through the scope manager, so a type-only `interface Promise` still leaves the global reported.
- **`typescript-dev-toolkit/prefer-dedent` reports an array of string and template literals joined with `'\n'` or `'\r\n'`, and fixes it to a `dedent` template.** An array holding anything else (an identifier, a call, a spread, a hole) builds its string at runtime and is left alone. The fix reverses what `dedent` 1.x does as a tag, so the string stays byte-identical: `dedent` trims the whole result and only afterwards decodes `\n` / `\r` escapes, so a leading or trailing run of line breaks (an `''` first or last element) and every carriage return are written as escapes, and backticks and `${` are escaped. It keeps the report and offers no fix where that cannot hold: a backslash (`dedent` passes it on raw, and decodes `\n`, `\x..` and `\u..` even inside interpolated values), edge whitespace `dedent` would trim, a template literal with expressions (its values may carry line breaks or indentation), and comments inside the call. It reuses a visible default import of `dedent`, or adds `import dedent from 'dedent'` under a free name, so a file the fix touches needs `dedent` among the package's dependencies (`devDependencies` for a test, `dependencies` for shipped code). `prefer-dedent.test.ts` runs every fixed shape through the real `dedent` and compares it with the original join. `import-fix.ts` holds the import lookup and insertion this rule shares with `prefer-noop-async`. **Its `ignoreInsideCallsTo` option names functions whose callbacks are serialized and run elsewhere** (`obsidian-dev-toolkit` sets `evalInObsidian` and `pollInObsidian`): a join inside a function nested in such a call's arguments is not reported at all, because the module's imports, `dedent` included, are not in scope where it runs, and the fix threw `dedent is not defined` there while every static gate stayed green. A name matches a bare callee or a non-computed member property; a join in those arguments outside any function runs in the calling process and is still fixed.
- **Shared `no-restricted-syntax` entries require named patch arguments.** Inside a `patchHandler` property, numeric indexing of `originalArguments` or the older `originalArgs` spelling is rejected, including optional access and `params.originalArguments[0]`. Destructure the tuple using the patched signature's parameter names; array holes and forwarding the whole tuple remain legal. The syntax check does not resolve renamed tuple bindings or validate binding names against types.

### Type Validation (manual `skipLibCheck` wrapper)

`tsconfig.json` sets `skipLibCheck: true`. This is a deliberate exception to the usual "never weaken `@tsconfig/strictest`" stance: it lets `tsc` type-check our `.ts` files without failing on broken upstream `.d.ts` files we do not control (e.g. a given version's `obsidian.d.ts`, which has shipped `HistoryHandler`/`PromiseWithResolvers` type errors).

The declarations we author (`src/@types/**`, `mnaoumov/obsidian-dataview:src/@types/**`) are still fully validated. `buildCompileTypeScript()` (run by `build:compile`) does two passes:

1. `tsc --build --force` — the normal compile, with `skipLibCheck: true`.
2. An in-memory re-check via `checkProjectTypes()` (`src/check-project-types.ts`) with `skipLibCheck: false`, reporting **only** diagnostics whose source file is under the project root and outside `node_modules`. It prints `Ignored N diagnostic(s) outside the validated set.` — when upstream is fixed and `N` reaches `0`, the workaround is no longer doing anything and `skipLibCheck` can go back to `false`.

`checkProjectTypes()` / `parseTsConfig()` / `toCanonical()` are exported as a reusable primitive, so consuming plugins inherit the same resilience through the shared `buildCompileTypeScript()`.

### L8. Re-export a type from an ESM-only package through its `import type`, never `export … from`

- `build:validate-declarations` type-checks the emitted `dist/lib/cjs/**/*.d.cts` under CJS resolution. There, any reference to an **ESM-only** dependency (`type-fest`, and anything else without a CJS entry) fails with **TS1479** unless the module specifier carries `with { 'resolution-mode': 'import' }`.
- TypeScript's declaration emit adds that attribute **only to import declarations**. It does NOT add it to a re-export, so `export type { PackageJson } from 'type-fest';` compiles fine in `src/` and then fails the `.d.cts` validation — a break invisible to `lint`, `test`, and `build:compile`.
- Re-export the binding already imported at the top of the file instead (`import type { PackageJson } from 'type-fest';` … `export type { PackageJson };`). The resolution mode stays attached to the import, and both the `.d.cts` and `.d.mts` emit the bare `export type { … };`.
- `unicorn/prefer-export-from` actively pushes back toward the broken form, so the re-export needs an `// eslint-disable-next-line unicorn/prefer-export-from -- …` naming this reason. See `src/npm.ts` for the reference case.
- (cannot be forced by ESLint — the opposing rule is the one ESLint has; `build:validate-declarations` is the check that catches it)

### L15. A function serialized into the emitted banner may only reference its own module — and `globalThis` stays spelled out

- `preprocess-plugin.ts` ships code as **text**: `makePreprocessBanner()` (`src/bundlers/esbuild-impl/preprocess-plugin.ts`) builds the esbuild banner out of `String(fn)`, so what lands in every consumer's bundle is source text, not a linked module. Two consequences that no type-check or unit test catches, because both are correct in the builder process and wrong only in the emitted artifact:
- **Cross-module calls do not survive.** esbuild compiles an imported call to `(0, import_module.fn)(…)` in the CJS dist — `makeValidVariableName` appears exactly that way in `dist/lib/cjs/script-utils/bundlers/esbuild-impl/preprocess-plugin.cjs` — naming a binding the emitted bundle does not have. Only **same-module** references stay bare identifiers. That is why `ensureBrowserProcess` / `keepName` live beside `initCjs` / `initEsm` rather than in a tidy `banner-shims.ts` (drafted once, then deleted for this reason), and why `makePreprocessBanner()` serializes the shims alongside the `init` function that calls them.
- **The two packages split the banner along that line, and the split is why each half is self-contained.** The generic plugin in `typescript-dev-toolkit` owns the shims, `initCjs` / `initEsm` and the shared IIFE. The Obsidian plugin in `obsidian-dev-toolkit` (same file name) calls it with `additionalBannerInitFunctions: [patchObsidianRequire]` for CommonJS and an `activeWindow`-reading `cjsImportMetaUrlProvider`, and each of those is serialized as its OWN `(fn)()` after the shared scope. So `patchObsidianRequire` cannot call `ensureDisposeSymbols` or `extractDefault` from the generic module (it would compile to `(0, import_preprocess_plugin.extractDefault)` in `obsidian-dev-toolkit`'s CJS build) and carries its own `extractDefault`. The generic CJS banner has no `require` patch, so the three `typescript-*` packages' CommonJS output loads under plain Node, where the patch's `globalThis.app.isMobile` read used to throw on the first non-built-in `require`.
- **A helper that is referenced but not serialized fails silently**, degrading to whatever the consumer's global scope holds under that name. `globalThisRecord['__name'] ??= name;` shipped for years resolving `name` to `window.name` — a string, not a function. Nothing threw, because nothing called it.
- **Never let `lint:fix` shorten `globalThis.x` to `x` in banner code.** `unicorn/no-unnecessary-global-this` autofixes `globalThis.process` → `process`, which is equivalent in a module but not in the banner: there a bare `process` is a free identifier, so reading it where the host has none throws a **ReferenceError** — precisely the case `ensureBrowserProcess` exists to handle. The line carries a disable comment saying so; keep it.
- **Verify against the built `dist`, never only the source.** Run `npm run build`, then execute the banner sliced out of `dist/lib/cjs/*.cjs` and `dist/lib/esm/*.mjs` against the host shapes you care about. The unit tests call `String(fn)` on vitest's transform, which is exactly the compilation step that differs.
- **The banner is also where `Symbol.dispose` / `Symbol.asyncDispose` get their fallback (`ensureDisposeSymbols`), and it has to stay there rather than beside each disposable.** A disposable keys its method with the literal `[Symbol.dispose]`, while esbuild lowers every `using` to a lookup through its `__knownSymbol('dispose')` helper, which falls back to `Symbol.for('Symbol.dispose')`. On an engine without the well-known symbol the literal key is `undefined`, the method lands under the string `"undefined"`, and every `using` throws `Object not disposable` — which is how a link conversion threw on iPadOS while working on desktop. Filling the slot with the registry symbol, once, before any module body runs, makes both sides agree for every producer at once. `preprocess-plugin.test.ts` pins it end to end: it bundles disposables declared in the shape of `typescript-lib`'s `CallbackDisposable` / `AsyncCallbackDisposable` (not the library's own, whose built copy already carries the banner, so the control below could never fail) and runs them in a `node:vm` context whose `Symbol` lacks both symbols, with a no-banner case that must still throw, so the simulated engine cannot quietly stop simulating anything.
- (cannot be forced by ESLint — a custom rule could flag imported identifiers inside the serialized functions, but not the `globalThis` autofix interaction)

### L18. The Windows command-line budget is not 8191 — measure what you can, reserve for what you cannot

- `exec()` has **two** length limits on purpose and they must not be collapsed into one. `getMaxCommandLength()` is the raw platform maximum and guards a command that cannot be split; `getMaxBatchCommandLength()` subtracts `WINDOWS_CHILD_EXPANSION_RESERVE` and sizes an `ExecArgument` batch. Splitting a batch costs one extra sequential invocation, so that side may be wrong in the safe direction; rejecting a command that cannot be split is fatal, so that side must stay exact.
- **The assembled command is not what `cmd.exe` sees.** Two costs are spent after any naive length check: node's `spawn(…, { shell: true })` wraps the command as `%ComSpec% /d /s /c "…"`, and `spawnViaShell` then runs `cmdEscapeCommandLine` over it, which grows a list of quoted paths by a few percent. Both are ours, so `getEffectiveCommandLineLength()` computes them rather than guessing — and its platform branch must stay in sync with `spawnViaShell`'s.
- **A third cost is not computable and must be reserved for.** `npx <tool> <args…>` is a *chain* of `cmd.exe` lines: `npx.cmd` re-expands `%*`, the tool's `.bin/<tool>.cmd` shim does it again, and each hop re-quotes what it forwards. Every line in the chain faces the same 8191 limit and every one is longer than ours. Measured on one repo's 187-file list: a `markdownlint-cli2` invocation **assembled at 7051 chars** — 1140 under the limit — died with `The command line is too long.`
- **The symptom names nothing wrong with the content**, and it is size-dependent, so a repo passes until the day it adds a few files and does not. Both halves of `markdownlint.ts`' `lint()` are exposed, not just the `linkinator` one. If it ever returns, raise the reserve; never lower it.
- (cannot be forced by ESLint — the limit is a property of the spawned process's own shim chain)

### Framework

- Vitest with explicit imports (globals: false) — always import `describe`, `it`, `expect`, etc. from `'vitest'`
- Test environment: `node` by default; use `// @vitest-environment jsdom` directive for browser tests
- Coverage provider: v8
- **`unit-tests:obsidian` runs on `pool: 'vmThreads'`, and the one thing that costs is `vi.stubGlobal('window' | 'document', …)`, which throws there.** The pool builds the jsdom once per worker instead of once per test file — measured 2026-09-15 at `test:coverage` 149.79 s → 56.88 s and that project alone 36.06 s → 9.92 s, since Vitest's own advisory had 67% of tracked time going on jsdom construction. Isolation is unaffected (probed directly: no DOM, `globalThis` or prototype state crosses files in one worker) and so is coverage (`coverage/lcov.info` byte-identical to the default pool's over a six-file subset). But a VM context's `window` and `document` are **non-configurable accessors** on its global, so `vi.stubGlobal` fails with `Cannot redefine property: window` — JS semantics, not something to route around. Every other global (`FileReader`, `Image`, `getComputedStyle`, `fetch`, `electron`) stubs normally. A test that needs to stub one of those two goes in `GLOBAL_STUB_TEST_FILES` in `scripts/vitest-config.ts`, which is the sibling `unit-tests:obsidian-global-stubs` project on the default pool. The other remedy the advisory names, `isolate: false`, was measured and is not a trade-off worth revisiting: **91.62 s, slower than the 36.06 s baseline**, with 68 tests failing on shared state. **The shared `defineObsidianPluginVitestConfig` gives every consuming plugin the same pool** on its `unit-tests` project, with the same escape hatch as a context field, `globalStubTestFiles`, which emits a `unit-tests:global-stubs` sibling only when non-empty. So check a suite by running it with `--pool=vmThreads`, not by grepping it. **The VM context also LACKS globals, silently:** Vitest copies only a fixed handful of Node globals into the `jsdom` window, so `crypto.subtle`, the Web Streams classes, `CompressionStream`, the `Performance*` classes and `URLPattern` are absent under the VM pool while present under the default one. A plugin's canvas hashing failed on `crypto.subtle.digest`, and feature-detecting code would instead pass while testing a fallback Obsidian never runs. `restoreNodeWebGlobals` (`mnaoumov/typescript-test-toolkit:src/node-web-globals.ts`), called from `setup()`, defines each missing name from its Node module and leaves present ones alone. And the project's `execArgv` flag that turns off Node's Web Storage still reaches a `vmThreads` worker: `process.execArgv` carries it and Node's own `localStorage` descriptor is absent, as under `threads`.
  - **A per-file module realm is why `installWarningsAsErrors` marks its listener instead of comparing identity.** Under this pool each test file evaluates the module afresh while `process` stays shared per worker, so an identity check matches nothing and every file appends another `'warning'` listener until Node's `MaxListenersExceededWarning` — which that listener rethrows, failing a blameless file. Any other per-worker registration added here needs the same treatment.
- **A unit test that builds a real TypeScript or ts-morph program, esbuild bundle or resvg image belongs in the `unit-tests:slow` project (`SLOW_TEST_FILES` in `vitest.config.ts`), not behind a per-test `{ timeout }`.** That project gives each test 180 s on at most two workers, and so does `unit-tests:eslint-typecheck`; the slow project gives each hook 180 s too, for a file that builds its program once in a `beforeAll` (`api-docs.test.ts`). On 2026-10-26 a release could not pass its preflight while other work held the machine at 100% CPU: `buildLibraryTypes` cases went past their 30 s override and two ts-morph cases past the 5 s default, three runs in a row, each on timeouts only, with 4 to 11 s alone. A per-test option also overrides the project budget, so a file in that project carries none.
- **Investigate a `unit-tests:eslint-typecheck` timeout by running the named file alone (`npx vitest run <file>`).** That project runs `maxWorkers: 1` with `isolate: false` (`vitest.config.ts`) and every `@typescript-eslint/rule-tester` case builds a type-aware program, so it is sensitive to machine load: one case was measured at 141 s under load against its former 60 s budget. Its project budget is now 180 s. A bare timeout alone does not establish a regression or rule it out; compare the isolated run and its assertions. Do not run `find-overexposed` or another gate concurrently with `test:coverage` — that alone was enough to fail two runs on 2026-09-02, and a failed run also wipes `coverage/`, so there is no lcov left to decode afterwards.
- **`reporters` is PINNED to `['default']`, because vitest's fallback is not one reporter but two — and the one an AI session gets prints no per-file line at all.** An unset `reporters` resolves to `isAgent ? 'minimal' : 'default'`, and `std-env`'s `isAgent` is true inside every AI coding session (it reads `AI_AGENT` plus a dozen tool-specific variables). `MinimalReporter` extends the default one with `summary: false`, `silent: 'passed-only'`, and a `printTestModule` that returns early unless the module FAILED, so a passing file prints nothing at all. Measured here 2026-09-23 on `unit-tests:script-utils` (43 files, vitest 5.0.1), the same command both ways: **0 per-file lines over a 13-line log unset, 46 over a 58-line log pinned**. The pin lives in `DEFAULT_VITEST_REPORTERS` (`src/test-runners/vitest-config.ts`, re-exported by `mnaoumov/obsidian-dev-toolkit:src/test-runners/vitest-config.ts`), is applied by `defineObsidianPluginVitestConfig` so **every consuming plugin gets it**, and is imported by `scripts/vitest-config.ts` rather than restated, since this repo's own config predates the factory. Under vitest 4 none of that existed, the run said only `167 passed (168)`, and a reporter reconciling the specifications `onTestRunStart` hands over against the modules that actually reported was the only way to learn which file was lost. Lifting such a reporter into this library was considered on 2026-09-23 and DROPPED on the measurement above: on vitest 5 it would be a module, a test file and a 100%-coverage burden for every consumer, carrying a claim that is no longer true.

- **Choose the bump from `git log <lastTag>..HEAD`, never from the change you happen to be working on — and the preflight now REFUSES a bump below what that range forces.** `npm run version -- <type>` takes the type as an argument, so the release ships every commit accumulated since the last tag, which is routinely more than the current task's. `assertVersionUpdateTypeMeetsBumpFloor` derives the floor from the range — a `!` before the subject's colon or a `BREAKING CHANGE:` / `BREAKING-CHANGE:` footer forces a major, a `feat` type forces a minor — and throws naming every forcing commit with its short hash, its subject and WHICH marker forced it. **It only refuses a bump that is too LOW**; a deliberately higher one passes, and there is deliberately no opt-out flag, because an opt-out is what gets reached for reflexively and the legitimate escape (bump higher) already exists. **Asking a human to scan and verifying nothing did not hold, twice.** `96.5.1` was chosen as a patch for a one-line `fix` and shipped six unreleased `feat:` commits with it — the instruction above was written after it. `105.1.0` then shipped as a MINOR carrying `feat(vitest-config)!` (`09457e84`, landed on `main` as `a0f025cf`), so every consumer on a caret range took a breaking change with no version signal. Verified against the real history: the derivation reports `105.0.0..105.1.0` as **major** naming both `!` commits, and `105.1.0..105.2.0` as **minor**, which is what `105.2.0` actually shipped as.
  - **It runs in the preflight, beside the TTY refusal and for its reason** — seconds, not after the whole check-and-build gate, and nothing has been written when it throws. It is **not** governed by `shouldRunChecks`: `--no-checks` buys a fast release by skipping verification of the CODE, and the bump a fast release publishes is as public, and as unfixable afterwards, as any other.
  - **The floor scans EVERY commit in the range, deliberately not `--first-parent`, which is where it differs from the changelog generated over the same range.** The changelog is first-parent because it publishes one line per landed change; a breaking change is breaking whichever parent it arrived on. Concretely, `toChangelogEntry` lifts only the FIRST line of a merge body onto a default merge subject, so a `BREAKING CHANGE:` footer written on a branch commit reaches no first-parent history at all — and the footer is the one breaking signal Conventional Commits puts in the body rather than the subject. The cost is over-detection (a branch whose breaking commit was reworked into a non-breaking merge still forces a major); that direction is safe, because an over-bump costs a consumer nothing and the message names the commit.
  - **The bump actually taken is measured off the resulting version, not read off the type string.** `prerelease` advances whichever line an earlier `premajor` or `preminor` already chose, and an explicit `x.y.z` says nothing until it is compared — so `toEffectiveBumpLevel` compares the new version's `major`/`minor` coordinates against the baseline tag's, which is one rule for all of them and is how a consumer's caret range reads it anyway.
  - **No resolvable baseline tag means no floor, loudly.** A first release, or one whose previous tag was deleted, falls back to no baseline (the changelog step already does the same), and the gate logs a `Version` debug line and takes the bump as given. Deriving a floor from the full history of a repo about to cut `1.0.0` would refuse it over commits that predate the concept of a published surface.
  - **`resolveLastReleasedTag` is shared with the changelog step on purpose**, so the two can never disagree about which commits are being published — the floor is derived over exactly the range the changelog will describe.
- **A commit that reaches `main` and is then superseded still lands in the changelog**, which is generated from commit messages (`git log <lastTag>..HEAD --format=%B --first-parent`). If an approach is reworked before it is ever released, squash the unreleased commits rather than letting the changelog announce a state that never shipped (done for `96.5.1` — two `fix(build)!` commits carrying a `BREAKING CHANGE:` footer for an abandoned barrel change were squashed into one `fix(obsidian):` commit and force-pushed).

- **The changelog review is the only step that can block, and it is deliberately the last step before anything is written.** `updateVersion` settles the changelog on a scratch copy under the OS temp folder *before* `updateVersionInFiles`, so interrupting the review leaves the working tree pristine and the release simply re-runnable — the earlier order bumped `package.json` / `manifest.json` / `versions.json` first, and a stop at the editor then stranded a dirty tree that `assertGitRepoClean` refused to re-release (hit cutting `App Update Notifier` 1.0.0).
- **The GitHub release body is the changelog section delimited by LINES, terminating at the next `'## '` heading or at end-of-file — never by a regex that requires a following heading.** `getReleaseNotes` used to match `\n## <version>\n\n(…)\n\n##`, whose trailing `##` is mandatory. Sections are PREPENDED, so the newest one is bounded by the previous release only once a previous release exists: on a **first release** the match was `null` and the body silently shipped as nothing but the `**Full Changelog**` link. It reached the store on five plugins' `1.0.0` — `nested-properties`, `edit-link-alias`, `backlink-full-path`, `refresh-any-view`, `app-update-notifier` — i.e. exactly the release where notes matter most, and no warning was ever emitted. The same regex also truncated a section at its own `###` sub-heading, because it treated the delimiter as if only version headings could produce it. `extractChangelogSection` now scans lines and stops at `'## '` **with the trailing space** (so `###` stays inside the section) or at the end of the file.
- **The first `##` heading in `CHANGELOG.md` is a HEADING, not a tag — `prepareChangelog` verifies it resolves (`git rev-parse --verify --quiet refs/tags/<heading>`) before spending it as a git revision.** It used to hand the heading straight to `git log <heading>..HEAD`, so a repo that had never been tagged died on `fatal: ambiguous argument '0.0.0..HEAD'` — and died at the very END of the release, after the entire preflight had been paid for. Two ways in: a hand-written `## 0.0.0` placeholder in a repo awaiting its first release (hit cutting `Advanced Markdown Export` 1.0.0), or a tag deleted after the fact. An unresolvable heading now falls back to the full history, with a `Version` debug line naming it — visible where it matters, because the interactive review is right there to trim an over-included range, and the debug line is all the non-interactive paths get.
- **A merge subject git wrote itself never reaches the published changelog: the generator rewrites it, and the release refuses what it cannot rewrite.** For a non-ff merge the first-parent commit IS the merge commit, so its subject is what `git log --format=%B --first-parent` yields and what ships — a default `Merge branch 'x'` therefore publishes a branch name as a changelog entry, which says nothing about what changed and, on a branch named after a private tracker item, decodes to nothing at all. The convention that a merge takes the same Conventional-Commits subject as the branch commit it lands was held up by nothing but the interactive review, and `--no-changelog-editing` — the flag an unattended release actually uses — skips that entirely; one sweep across this workspace found twelve such published entries in a single repository. `toChangelogEntry` now lifts the subject out of the merge BODY whenever the subject matches `MERGE_SUBJECT_REG_EXP` (`Merge` plus a word boundary, which covers `branch`, `branches`, `remote-tracking branch`, `pull request`, `tag` and `commit`), because that is where the real message usually already sits: the author wrote it and the generator used to throw it away. A merge with no body has nothing to lift, so `assertChangelogHasNoMergeSubjects` throws and names the offending lines. **The same regex drives both halves**, so the refusal is reachable only for what the rewrite could not repair. The check runs at the END of `prepareChangelog`, on the settled content — one site covering the commit-derived bullets, `--changelog-file` notes and whatever a review left behind, still before anything is written — and it scans only the section being published, so an entry that already shipped cannot block every future release.
- **The new changelog section is linted BEFORE it is written, because the release's only `lint:md` runs before it exists.** The ordering used to guarantee the gap: `gate()` runs `lint:md` as its third step, and `prepareChangelog` settles the section long after it, so every character of a new section entered the repository after the only check that could have looked at it. The release still succeeded; the defect landed on `main` inside the `chore: release <version>` commit and turned the NEXT gate red — anyone's branch, plus the next release's own preflight. This repository's `## 101.3.0` section is the historical instance: a hand-added bullet hard-wrapped at ~100 columns, which `git log -S` places in `c10d6bc6 chore: release 101.3.0`, the release commit itself. The generator's own bullets cannot fail it (one `toFirstLine` per commit, which cannot wrap); the two paths that carry prose — the interactive review and `--changelog-file` — could and did. `prepareChangelog` now lints the settled section through `lintMarkdownContent`, beside `assertChangelogHasNoMergeSubjects` and for the same single-site reason, while the working tree is still pristine and the release is still cleanly re-runnable. **Interactive runs re-open the editor with the findings printed above the prompt**, since the author is sitting right there; a review that hands back byte-identical text is the author declining, and stops the release rather than looping. `--changelog-file` and `--no-changelog-editing` have nobody to ask, so they throw on the first finding. **Only the NEW section is linted**, wrapped in a minimal `# CHANGELOG` + `## <version>` document: the whole file is the honest check and is the wrong one, because it fails a release on a section somebody shipped years ago — the shape the five open `lint:md`/`spellcheck`-red-on-`main` items across this fleet are all stuck in. The reported line numbers are the written file's own, which is not a coincidence: a section is prepended, so the minimal document is character-for-character the head of the file about to be written.
- **A section GENERATED from commit subjects that nobody will review (`--no-changelog-editing`) gets `lint:md:fix`'s fixes first** (`composeChangelogNobodyReviews`, through `fixMarkdownContent` in `src/linters/markdownlint-content.ts`), and the findings check then refuses only what no rule could fix. A `--no-ff` merge is made with `HUSKY=0` and an issue-closing merge takes the issue title verbatim, so no commit hook ever checks the subject that becomes the entry: an Obsidian plugin's release was refused three times over a plugin name `plugin-name-as-code` would have wrapped in backticks. `markdownlint-cli2`'s own `fix` skips `nonFileContents`, so `fixMarkdownContent` collects the findings through a function output formatter (`optionsOverride.outputFormatters`) and applies their `fixInfo` with markdownlint's `applyFixes`, one pass as `lint:md:fix` makes. Prepared notes and a reviewed section are never rewritten, and only the new section is touched. The release prints how many findings it fixed, because the notes then differ from the subjects.
- **A section nobody will review is checked BEFORE the gate as well** (`assertNonInteractiveChangelogIsPublishable`, beside the bump floor and, like it, not under `shouldRunChecks`). With `--no-changelog-editing` or `--changelog-file` the new section is decided by what is already committed, so the lint, spellcheck, merge-subject and forbidden-pattern checks are answered in seconds instead of after the preflight. With a review due nothing is checked early, because the author can still fix a finding in the editor. `prepareChangelog` still checks the settled text afterwards.
- **The section is SPELLCHECKED in the same window, and that half is the one this fleet actually bleeds from.** All five of the `main`-is-red items across this fleet are `cspell` rather than markdownlint — each one a coined word published in an old release note, so the repository cannot cut a release until somebody edits history or adds the word. `getChangelogSectionFindings` runs `lintMarkdownContent` and `spellcheckContent` over the SAME minimal document, and neither short-circuits the other: an author with a hard-wrapped line and a coined word is told about both in ONE round of the review. Each finding is tagged with the npm script that produced it, so the error and the editor banner name `lint:md`, `spellcheck` or `lint:md and spellcheck` — naming both unconditionally would be a lie half the time, and would send an author to look at a check that passed.
- **A generated bullet links the issues its commit body names** (`toChangelogEntry`, `parseIssueReferenceLine` in `src/version.ts`). A body line that is a keyword (`Refs`, `Re`, `Fixes`, `Closes`, `Resolves`, `Implements`, any tense, optional colon) followed by references and nothing else (`owner/repo#n`, an issue or PR URL, `#n`, comma- or `and`-separated) appends them to the bullet: `- fix: tidy the parser (<https://github.com/owner/consumer/issues/1>)`. A prose line that merely opens with `Fixes` adds nothing, and a reference the subject already shows is not repeated. A cross-repository reference is rendered as its URL in angle brackets, because GitHub shows it as the same short link and the section's spellcheck skips a URL but not a repository name. This exists for a fix made here for an issue in another repository: the subject cannot carry that number, so without the body line the release names no issue at all. **Only the FIRST-PARENT commit's body is read**, so for a `--no-ff` merge the merge message must carry the line, not only the branch commit.
- **`spellcheckContent` SHELLS OUT where `lintMarkdownContent` calls a library, and the asymmetry has a reason rather than being an oversight.** `cspell` does export a CLI-layer `lint(fileGlobs, options, reporter)` that looks like the exact analogue of `markdownlint-cli2`'s `main`, and it cannot be used here: the only way to hand it content that is not on disk is a `stdin://` glob, and its reader is `streamConsumers.text(process.stdin)` — the HOST process's own stdin, which the release's interactive review also uses. Using it would mean monkey-patching `process.stdin` for the whole process. So the content goes to a child's stdin under `cspell lint --no-progress --no-must-find-files --no-summary --no-color stdin://<posix path>`. **The `stdin://<path>` form is what makes the check the repository's own**: the virtual document is attributed to a REAL path, so `cspell.json` beside it — its `words`, its dictionaries, its `ignorePaths` — resolves exactly as it would for the written file. A temp file outside the repository loses all of that, which is why it is not used; `src/cspell-content.integration.test.ts` pins the distinction by feeding a word that exists in no dictionary anywhere except this repository's own list. Findings arrive on `stdout`, one per line, and the summary on `stderr`; a non-zero exit with nothing on `stdout` is `cspell` itself failing and throws, because returning `[]` there would read as a clean document and let through the very thing the module exists to catch. **A test file that needs an unknown word has to ASSEMBLE it** (`['lint', 'able'].join('')`) — `spellcheck` reads the test files too, so writing the literal puts the defect it is testing for into the repository.
- **A section carrying the maintainer's PRIVATE vocabulary is refused too, and the list of what counts as private lives outside every repository.** Every commit subject since the last tag ships verbatim into the new section, so a subject naming an internal tracker id or a private project short name lands in a published file inside the release commit. The list cannot be a literal here (that ships it to every npm consumer) or a checked-in per-repository config (that publishes it in every public repository using it, permanently), so `assertChangelogHasNoForbiddenPatterns` reads it from the file the `FORBIDDEN_PATTERNS_FILE` environment variable names — set in the shell or in a gitignored `.env` — via `src/forbidden-patterns.ts`. One pattern per line; blank lines and `#` lines are skipped; a `/source/flags` line takes its flags, any other line is a case-sensitive source. **Unset is a no-op, so a consumer who never configures it sees no change; set but unreadable THROWS**, because a guard that switches itself off when its list moves is the silent failure it exists to stop. It runs beside `assertChangelogHasNoMergeSubjects`, on the settled new section only and before anything is written, so the refusal leaves the tree pristine. The error prints each offending line and the matched text, never the pattern.
- **`lintMarkdownContent` goes through `markdownlint-cli2`'s API, never `markdownlint`'s string API, and that is the whole point of the module.** The question it answers is *"would this repository's `lint:md` have failed on this text?"*, and only the `markdownlint-cli2` layer knows: it finds `.markdownlint-cli2.mjs`, loads it through `jiti` (the configuration is TypeScript in every repo here), merges the repository's own overrides over the shared defaults, and loads the custom rules. `main({ directory, noGlobs: true, nonFileContents, logError })` lints in-memory content as a named path with that configuration. `noGlobs` is load-bearing: without it the configuration's own `globs` are expanded too and a one-document check lints the whole repository. The shared configuration is passed as `optionsDefault` — a BASE the repository's own configuration overrides key by key — for the repository that has none yet, where markdownlint's stock defaults would otherwise apply and `MD013/line-length` would fail an ordinary release note at 80 columns. Since a repository's own configuration always wins, that default can only ever miss a finding, never invent one. The package ships JSDoc types and no declaration, so the subset used is declared in `src/linters/markdownlint-types/@types/markdownlint-cli2.d.ts`, beside the configuration-schema types.
- **A release without a TTY refuses in the preflight, not after the gate.** `npm run version` checks `process.stdin.isTTY` right after the git/gh assertions and before the checks and build, so an agent- or CI-driven run fails in seconds instead of paying ~17 minutes and then hanging on `code -w`. Release unattended with `--changelog-file <path>` (prepared release notes replace the commit-derived bullets) or `--no-changelog-editing` (accept the generated bullets as is).
- **A successful `git commit` is not proof the release commit landed, so `updateVersion` checks where it went before tagging and again before pushing** (`assertReleaseCommitLanded`). It reads the branch and `HEAD` before the gate (`readGitHeadState`), and after the commit requires the same branch, a commit whose parent is the start commit, and the `chore: release <version>` subject; the tag then names that verified SHA rather than `HEAD`. A plugin release on 2026-10-21 exited 0 with its tag and GitHub release on the commit before the bump: another process had checked out a different branch in the same working tree during the release, the commit landed there, and the checkout was switched back a second before `git tag` ran, leaving the bump staged. The reflog is what showed it, and is where to look if the check ever fires.
- **In PowerShell, QUOTE the `--` separator: `npm run version '--' <type> --no-changelog-editing`.** PowerShell consumes a bare `--` as its own end-of-parameters token, so npm never receives the separator and parses the following flag as npm's own config — `npm run version -- minor --no-changelog-editing` dies with `EUNKNOWNCONFIG … Unknown cli flag: --changelog-editing` before `scripts/version.ts` starts. The positional bump type forwards either way, which is what makes the error read like a bad flag name. This is a shell-quoting issue, not an npm 12 regression: with the same npm 12.0.2 the bare form forwards correctly from bash, and the quoted form forwards correctly from PowerShell (verified both ways, 2026-09-01). `npx jiti scripts/version.ts <type> --no-changelog-editing` also works from any shell — the npm script is only `jiti scripts/version.ts`, so it is the same code path with no separator to lose.
- **Once the GitHub release exists, `publishGitHubRelease` closes the issues it carries, but only the ones a commit names with a CLOSING KEYWORD** (`src/released-issues.ts`). It reads every commit since the previous tag (`git describe --tags --abbrev=0 <version>^`; the whole history when there is none, and deliberately not `--first-parent`, for the bump floor's reason), and closes each open issue of this repository named as `fixes #12`, `closes owner/repo#12` or `resolves <issue URL>` (GitHub's nine keyword forms), with `Fixed in <release URL>` when it carries a `bug` label and `Implemented in <release URL>` otherwise. **A bare mention (`re #12`, `(#12)`) closes nothing**: it is often one step of unfinished work, and nothing the release can read says whether the rest has landed, so those issues are printed as left open for the maintainer. **An issue already closed as completed still gets the link**, because GitHub closes a keyword-named issue itself when the commit reaches the default branch — at merge, before any release, and with no release named — unless one of its comments already carries this release's URL, which is also what makes a re-run post nothing. Pull requests, issues closed as not planned and references into other repositories are skipped. **A failure there warns and never throws**: the release is already published, so a non-zero exit would read as a failed release. Opt out with `--no-issue-closing` / `shouldCloseReleasedIssues: false`.
- **`publishGitHubRelease` accepts both `npm pack --json` shapes, and must keep doing so — on the LIBRARY path only.** `publishGitHubRelease` never packs on the plugin path: its `if (isObsidianPlugin)` branch uploads whatever `dist/build/` contains, and only the `else` branch shells out to `npm pack`. `isObsidianPlugin` is true for any repo that has a `manifest.json` and whose package name is not `obsidian-dev-utils`, i.e. for every plugin built on this library, and false for this repo — so the `npm pack` branch is **this library's own releases**, and nothing else in practice (every other non-plugin repo here, `obsidian-integration-testing` and `obsidian-test-mocks` included, ships its own standalone `scripts/version.ts`, since every repo has to stand on its own). **A plugin release on a pre-98 version of this library is unaffected and never needs a bump on this account** — `Advanced Rename and Delete Handler` `1.1.1` was cut on version `96.5.2` of this library under npm 12.0.2 on 2026-08-31 and its GitHub release exists. Say this library, not "every release": the unscoped wording once led to a planned mandatory dependency bump that was not needed. The defect itself: npm 11 emits an array of pack results; npm 12 emits an object keyed by package name. The old code found the tarball name by scanning for the array's literal `'[\n  {'` opening, so every release of this library on npm 12 threw at the very LAST step — after the bump, changelog, commit, tag and push had all landed, leaving a public tag with no GitHub release and therefore nothing on NPM (`publish-npm.yml` triggers on `release: published`). It failed four releases of this library for four before being fixed. `parseNpmPackOutput` now locates the payload by parsing from each candidate start — the `npm notice` lines go to stderr, but the `prepare` script's own stdout precedes the JSON and may contain braces — and normalizes both shapes. **Any test mocking that output must mock the object shape**; mocking only the array is exactly what held coverage at 100% while the real command diverged. If a release of this library ever half-fails here again, `npm pack` has already written the tarball, so recovery needs no rebuild: `gh release create <version> dist/<tarball> dist/styles.css --title v<version> --notes-file <notes>`, the notes being the CHANGELOG section plus the `**Full Changelog**: …/compare/<prev>...<new>` line. `publish-npm.yml` fires on a manually-created release exactly as it would on a scripted one.

A release is two stages, split across two machines on purpose:

1. **Local** — `npm run version -- <patch|minor|…>` runs the checks and the build, bumps the version, writes the changelog, commits, tags, pushes, and creates the **GitHub release**. It stops there; it does **not** publish to NPM (`scripts/version.ts` no longer calls `publish()`).
2. **CI** — the `release: published` event triggers `.github/workflows/publish-npm.yml`, which reinstalls, rebuilds (`dist/` is gitignored, so the tarball's contents exist only after a build) and runs `npm run publish:npm` → `publish()` → `npm publish --tag <latest|beta>`, with the dist-tag derived from whether the `package.json` version is a pre-release.

The publish authenticates with **npm trusted publishing** (OIDC), not a token: the job's `id-token: write` permission lets the npm CLI trade a short-lived GitHub OIDC token for a publish grant, and provenance is generated automatically. Consequences worth knowing before touching any of this:

- **No `NPM_TOKEN` exists anywhere** — not in repo secrets, not in a local `.env`. `publish()` reads no credentials, and publishing from a developer machine is simply not possible (trusted publishing works only from the configured CI). A "how do I publish locally?" answer does not exist; re-run the workflow.
- **The npmjs.com side names the workflow file** (Package settings → Trusted publisher: owner, repo, workflow filename `publish-npm.yml`, case-sensitive). Renaming or moving that file breaks publishing with an auth error that says nothing about the rename — update the setting in the same change.
- Requires npm ≥ `11.5.1` and Node ≥ `22.14.0`; the version in `.nvmrc` satisfies both.
- `workflow_dispatch` is also wired up, so a failed publish can be retried from the Actions tab without cutting a new release.
- **Because CI rebuilds, anything the tarball needs must happen in `npm run build` — never in `scripts/version.ts`.** The release script runs only on the maintainer's machine, so a step placed there reaches the local `dist/` and nothing else, while CI publishes a `dist/` that never saw it. This is not hypothetical: the placeholder substitution used to live in `prepareGitHubRelease`, and every release from `94.7.0` (the one that moved publishing to CI) through `96.0.0` shipped a literal `$(LIBRARY_VERSION)`, which made `initPluginContext` throw `Invalid argument not valid semver` in every consumer. It is now the build step `build:stamp-generated`, which throws if the declaration it rewrites is missing, so an unstamped publish fails the build instead of reaching NPM. Verify a release with `npm pack obsidian-dev-utils@<version>` and grep the extracted `dist/lib/esm/generated-during-build.mjs` for the stamped value.

### Commits

- Conventional Commits enforced via commitlint + husky (commit-msg hook)
  - **The shared commitlint config also refuses a message matching the unpublished forbidden-patterns list — header, BODY and footer** (`typescript-dev-toolkit/no-forbidden-patterns`, `src/commitlint-forbidden-patterns.ts`). It reads the same `FORBIDDEN_PATTERNS_FILE` list the release's changelog refusal reads (see [Releasing](#releasing)), and passes when that is unset. It exists because the release check scans the generated changelog section, which carries commit SUBJECTS only: a private id in a commit BODY was scanned by nothing, and once pushed it sits in the public history for good, since cleaning a pushed commit with descendants means rewriting `main`. The commit-msg hook is the last point at which a body can be refused before it exists anywhere else. A set-but-unreadable list fails the commit, for the same reason it fails the release.
  - **It also SPELLCHECKS the header, the one part of a message that ships verbatim** (`typescript-dev-toolkit/spellcheck-header`, `src/commitlint-spellcheck-header.ts`). A release turns every subject since the last tag into a `- <subject>` changelog bullet and spellchecks that section before writing it, and that check refused 107.0.0 over a word in a subject pushed weeks earlier. It came after the whole preflight gate, when the only fixes left were rewriting `main` or hand-written release notes. The rule checks the header as that bullet, through `spellcheckContent` attributed to `CHANGELOG.md`, so the verdict is the release's own: the same `cspell.json`, `words` and `ignorePaths`. Like the release, it runs only where the project defines a `spellcheck` script, and a cspell that fails without reporting anything fails the commit. It costs one `cspell` spawn per commit. A default merge commit is skipped by commitlint's own ignores, so the body line a release lifts onto a default merge subject is still checked only at release time.
  - **It also runs `lint:md` over the header, built into the section the release would build from it** (`typescript-dev-toolkit/lint-md-header`, `src/commitlint-lint-md-header.ts`): `# CHANGELOG`, `## <version>`, `- <header>` with bare URLs autolinked, through `lintMarkdownContent` attributed to `CHANGELOG.md`, so a project's custom rules (an Obsidian plugin's `plugin-name-as-code`) answer as they will at release time. It runs only where the project defines a `lint:md` script. A release on 2026-10-23 passed its 25-minute preflight and was then refused over a pushed `docs(readme):` subject that rule flagged. A merge made with `HUSKY=0` skips this hook, which is why the release also checks a section nobody reviews before its gate (see Releasing).
  - **The config registers every rule through ONE inline plugin object, and it has to.** `@commitlint/load` stores every inline plugin object under the same `local` key, so with two objects the second replaces the first, and every commit then dies with `Found rules without implementation: typescript-dev-toolkit/no-forbidden-patterns`. A third rule merges its `rules` into that same object.
- nano-staged runs spellcheck, lint, format, and markdown lint on staged files via husky pre-commit hook
  - Opt out per-developer by setting `NANO_STAGED=0` (or `false`/`off`/`no`) in a gitignored `.env` (cross-platform, mirrors husky's own `HUSKY=0`); the `.env` is read by `getNanoStagedConfig()` in `src/nano-staged-config.ts`, which the `scripts/nano-staged-config.ts` entry calls. The commit-msg/commitlint hook still runs.
  - **That entry adds no writer of its own, so a staged `.astro` file (the docs site components) is only spellchecked.** The workspace entry added `*.astro` → `lint:fix` because the workspace's ESLint config loaded `eslint-plugin-astro`. This repository's config does not, and the plugin is not installed, so ESLint answers an `.astro` path with `File ignored because no matching configuration was supplied`, which `--no-warn-ignored` silences: the writer would run and check nothing. Add it back together with `eslint-plugin-astro`, never alone. It would take no `format` step, because none of the dprint plugins formats Astro.
  - **A positive integer `BULK_CORES` makes `getNanoStagedConfig()` execute one command at a time.** nano-staged 1.0.2 has no concurrency option. Its command generator visits config callbacks in insertion order before execution, so the original pattern callbacks collect their batched commands and a final catch-all drains them into one serial group. Pattern matching stays with nano-staged, custom writers and writer-before-spellcheck order are preserved, and invalid or absent budgets keep the normal parallel groups. Tests drive the installed command generator and runner, including repeated generation and failures. The hook remains `npx --no -- nano-staged`; consumers using the shared configuration inherit the limit after updating the toolkit.
  - **Two tasks that rewrite the same file must share one key.** nano-staged runs its per-pattern groups under `Promise.all` (`run()` in `nano-staged/lib/cmd-runner.js`) and sequences only the commands *inside* a single key's array (`runTask()`, a `for ... of await`), so `lint:fix` and `format` sit together under `*.{ts,tsx,mts}`. An earlier `templates/` exclusion moved `lint:fix` onto a `!(templates)*.{ts,tsx,mts}` key of its own and silently took that ordering away, so on every staged `.ts` the two writers raced and whichever finished last won (2026-09-23). Express a directory exclusion in the excluded tool's own config instead: `lint()` passes `--no-warn-ignored`, so a globally-ignored path handed to ESLint explicitly is skipped in silence and needs no key here.
  - **Spellcheck is PARTITIONED, never a catch-all `'*'` key, for the same `Promise.all` reason one level out.** A `'*'` spellcheck key runs concurrently with every writer key, so cspell read a file while `lint:fix` / `format` / `lint:md:fix` rewrote it in place — a spurious finding on a half-written file, or a pass over bytes that are not what gets committed (2026-09-24). So each writer key ends with `spellcheck --`, and one complement key spellchecks exactly the files no writer claims. That key is written in nano-staged's own glob dialect: `!(...)` compiles to a lookahead with NO end anchor (`!(*.md)*` would drop `notes.md.bak`), and a nested `!(?)` compiles to `(?!.)`, which is one — so the key reads `!(*.{ts,tsx,mts}!(?)|*.md!(?))*`. Unreadable, and pinned by `nano-staged-config.test.ts` against the INSTALLED `glob-to-regex.js`, so a nano-staged release that changes its dialect fails there rather than in a commit. A function-valued key cannot replace that negated key: nano-staged re-tokenizes a function's returned string with `stringArgvToArray`, which emits every quoted argument TWICE (unquoted and quoted), so a path with a space cannot be passed through one as itself. A repo-local writer (such as the workspace's `*.astro` → `lint:fix`) goes in through `getNanoStagedConfig({ additionalWriterTasks })`, which re-partitions around it; spreading the shared object and adding a key reopens the overlap for that key's files.
  - **Every key is a FUNCTION that batches the staged paths, because a string key puts them all on one command line** (2026-10-16). nano-staged appends a string task's files to a single command, so a commit staging 342 `.ts` files ran `npm run lint:fix -- <342 paths>` and failed on Windows with `The command line is too long.`, refusing exactly the whole-repo sweep commits that most need the hook. `toBatchedTask` costs each path with `exec.ts`' `getEffectiveCommandLineLength` against `getMaxBatchCommandLength` (the same budget, `npx` shim reserve included, that `ExecArgument` batching uses) less a `MAX_PATH` for the `npm.cmd` path nano-staged prepends, and runs every batch of one command before the next command, so the writer ordering above holds. Paths go relative to the working directory, and the tokenizer limit above is met by turning whitespace and quotes into `?`: every tool here takes globs, so `src/a?b.ts` still names `src/a b.ts`. One limit stays upstream: nano-staged's own final `git add -A -- <every file>` is one `git.exe` spawn, so past CreateProcess's 32767 characters of staged paths it fails with `spawn ENAMETOOLONG` after every task has passed (measured: 601 paths of ~100 characters).
  - **A shared task whose npm script the project does not declare is left out**, so every project can use `getNanoStagedConfig()`, whatever subset of `lint:fix`, `format`, `lint:md:fix` and `spellcheck` it has (2026-10-16). A writer pattern left with no writer is dropped, and its files fall to the spellcheck-only key. Without a `spellcheck` script no key spellchecks; with only that script the one key is `*`, because `!()*` compiles to a lookahead that rejects every path. It reads `package.json` when called, so the exported `obsidianDevUtilsConfig` constant still carries every task. `additionalWriterTasks` are kept as given, and may claim a shared pattern whose shared writer was left out.
  - The tasks run through the package manager that owns the tree — `bun run lint:fix --` on a bun tree, not `npm run lint:fix --`. The prefix comes from `getPackageManagerRunCommand()` and is resolved once when `nano-staged-config.ts` is first imported, so a lockfile change needs a fresh process to take effect (2026-09-02).
